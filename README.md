# AuditEnv: RL-среда для аудита дебиторской задолженности

Среда для дообучения и оценки моделей на задаче финансового аудита. Агент получает книги
вымышленной компании за один период (главная книга, счета, платежи, курсы валют, учётная
политика), исследует их через пять инструментов и сдаёт список расхождений с доказательствами.
Оценщик работает в отдельном процессе, сравнивает ответ с закрытой истиной один к одному и
выдаёт терминальную награду.

Всё работает офлайн на стандартной библиотеке Python 3.11: без сети, без GPU, без платных API и
без сторонних пакетов.

> Все компании, люди, счета, банковские записи и деньги вымышлены и сгенерированы. Курсы валют
> это синтетическое случайное блуждание, а не рыночные данные. Нет банковских карт, реальных
> платежей, персональных данных и регистрации финансовых аккаунтов. Это программная задача, а
> не профессиональное аудиторское заключение.

## Одна команда проверки

```bash
docker build -t auditenv:1.0.0 . && docker run --rm --network none --cpus 2 --memory 4g auditenv:1.0.0
```

Без Docker (нужен только Python 3.11), из корня репозитория:

```bash
python3.11 -m auditenv check        # то же самое: make check
```

`check` за одну-две минуты проходит семь стадий и возвращает код 0, только если прошли все:

1. все юнит-тесты (236 тестов: контракт, награда, атаки, генератор, изоляция, независимый
   валидатор, адаптер жюри);
2. определения проверок жюри через `judge_adapter.py` (блоки 1-4, см. ниже);
3. 10 train и 10 dev эпизодов заново генерируются из сидов и конфигов бит в бит как в `episodes/`;
4. независимая проверка данных и истины на этих 20 эпизодах и 20 эпизодах `holdout_sim`
   (секретная соль, новые сиды и параметры);
5. 20 парных проверок: точное воспроизведение по сиду и действиям, перестановка записей и замена
   ID сохраняют ответ оракула (с новыми ID) и награду;
6. базовые политики в закрытом режиме, когда политика, харнесс и оценщик работают в трёх
   процессах: оракул 1.0, «пометить всё» ниже 0, политики видят награду 0, каждый эпизод
   быстрее 60 с;
7. `trajectories/trajectories.jsonl`: есть все обязательные поля, закрытой истины нет.

Вывод последнего прогона в контейнере сохранён в [`reports/check_output.txt`](reports/check_output.txt).

## Подключение жюри: `judge_adapter.py`

Адаптер лежит в корне репозитория и реализует интерфейс из определений проверок от 20 ноября.

* Рабочая директория: корень репозитория (в контейнере `/app`).
* Запуск в контейнере: `docker run --rm --network none -v <каталог жюри>:/judge auditenv:1.0.0 python -c "import judge_adapter"`,
  дальше скрипт жюри импортирует `judge_adapter` (например, `docker run ... -v ./judge.py:/app/judge.py auditenv:1.0.0 python judge.py`).
* Закрытая соль для генерации берётся из `AUDITENV_SECRET`, путь журнала оценщика из
  `AUDITENV_EVALUATOR_LOG` (по умолчанию `<tmp>/auditenv-evaluator.jsonl`).

```python
import judge_adapter as ja

ja.generate_episode(seed, config, output_dir)   # config: наш конфиг генератора (или {"team_config": {...}})
env = ja.make_env()                              # клиент; среда и оценщик в отдельном процессе
obs, info = env.reset(seed, {"mode": "closed", "episode_dir": output_dir, "team_config": {}})
obs, reward, terminated, truncated, info = env.step({"name": "list_records",
                                                     "args": {"table": "ledger", "cursor": None, "limit": 50}})
ja.score_episode(output_dir, findings, inspection_steps)  # {"tp","fp","fn","precision","recall","f1","return"}
env.last_evaluation()                            # оценка последнего эпизода из журнала оценщика (сторона жюри)
ja.oracle_findings(output_dir)                   # верный findings.json из truth (сторона жюри)
```

| точка входа | поведение |
|---|---|
| `generate_episode(seed, config, output_dir)` | обёртка над нашим генератором; пишет `public/` (manifest.json, ledger.csv, invoices.jsonl, payments.jsonl, fx.csv, policy.json) и `private/` (truth.json, provenance.json) |
| `make_env().reset(seed, config)` | `mode="closed"` с `episode_dir`: загружает ровно этот эпизод, ничего не генерирует и не меняет ID; повторный reset начинает его заново. `mode="train"`: открытый режим. Без `episode_dir`: генератор с `seed` и `team_config`. `reset` и `score_episode` принимают и плоский каталог со всеми восемью файлами |
| `step({"name", "args"})` | пять действий; неизвестное имя или неверная оболочка дают ограниченную ошибку и тратят шаг |
| `score_episode(episode_dir, findings, inspection_steps)` | закрытый вызов оценщика; при неверной структуре `{"return": -1, остальные null}`, ошибка в журнале оценщика |

Наблюдения адаптера:

* первое: `{"task": str, "manifest": {...}, "policy": {...}, "remaining_steps": 100}`;
* дальше: `{"result": значение или null, "error": null или {"code", "message"}, "remaining_steps": int}`;
* `list_records` -> `{"records": [...], "next_cursor": str | null}`, первый курсор `null`;
* `get_record` и `get_document` -> сам объект записи или документа; `calculator` -> десятичная
  строка (`"0.1+0.2"` -> `"0.3"`); `submit` -> `{"accepted": true}` либо ошибка структуры
  `{"code": "invalid_submission", ...}`, без оценки правильности;
* в закрытом режиме `reward` всегда `0.0`, включая завершение, `info` пуст; в `train` терминальная
  награда приходит политике.

Таблицы и ключи: `ledger` (`row_id`), `invoices` (`invoice_id`), `payments` (`payment_id`), `fx`
(`fx_id` = `FX:<date>:<source_currency>:<target_currency>`, не случайный ID: дата и пара не
меняются при замене ID). `get_document` принимает `doc_id`. Поля записей совпадают с §03, перевод
имён не нужен. Время на эпизод 60 с от reset до завершения, включая время политики.

Четыре типа ошибок (имена `type` в findings и truth):

| тип в среде | ошибка из кейса | канонические `affected_ids` | сумма и валюта | допустимый набор доказательств |
|---|---|---|---|---|
| `duplicate_invoice` | дубль счёта | оба `invoice_id` | `total_minor` одной копии, валюта счёта | оба `doc_id` + по одной строке книги каждой копии |
| `payment_allocation` | пропущенное или частичное распределение платежа | `[payment_id, invoice_id]` | неприменённая часть распределения, валюта платежа | `doc_id` платежа + строка книги, где видна неприменённая или чужая сумма |
| `fx_conversion` | неверная дата или курс конвертации | `[payment_id, invoice_id]` | `\|проведено - верный пересчёт\|`, валюта счёта | `doc_id` платежа + `FX:` запись курса политики + строка с суммой в валюте счёта (+ строка клиринга, если применена часть) |
| `period_cutoff` | ошибка периода | `[invoice_id]` или `[payment_id]` | `\|total_minor\|` или `\|amount_minor\|`, валюта документа | `doc_id` (+ одна его строка книги, если он проведён) |

Все проверки жюри воспроизведены в [`tests/test_judge_adapter.py`](tests/test_judge_adapter.py) и
входят в `check`:

* блок 1: C01-C20 через `make_env()` на фикстурах C (чистый), E (одна ошибка), L (книга ≥101 строки) и ID U;
* блок 2: матрица D01-D20 ([`configs/splits/judge_matrix.json`](configs/splits/judge_matrix.json))
  генерируется через документированные настройки и проходит независимый валидатор;
* блок 3: 20 тестов matcher и награды с ожидаемыми значениями из определений (0.98, 47/150,
  -871/1050, -0.02, 0.90, 0.80, -1) и примеры M01-M12;
* блок 4: 20 пар P01-P20: копию эпизода в файлах переставляет и/или перенумеровывает независимое
  преобразование в стиле жюри (с правкой truth и provenance), копия подаётся через `episode_dir`,
  оракул с новыми ID после обратного отображения совпадает с исходным, метрики и награда равны при
  равном `inspection_steps`, сломанный набор доказательств награду не сохраняет.

## Быстрый старт без адаптера

```python
from auditenv import AuditEnv

env = AuditEnv(mode="train")                      # "eval" для закрытого режима
obs, info = env.reset(seed=7, config={})
obs, reward, terminated, truncated, info = env.step(
    {"action": "list_records", "args": {"table": "ledger", "cursor": None, "limit": 50}})
```

Родной формат действия `{"action": имя, "args": {...}}`, `step` принимает и строку JSON. Любое
действие сначала приводится к чистому JSON, поэтому Python-объекты с подменённым сравнением не
доходят до проверки. Лимиты действия (`policy.json -> limits`): до 1 000 000 символов JSON и до 64
уровней вложенности; вложенность проверяется по тексту до разбора, поэтому ответ среды не зависит
от версии Python. Не-JSON объект, слишком глубокое или слишком длинное действие это ошибка
`invalid_action`, шаг засчитывается, исключений нет (и через `judge_adapter.make_env()` тоже).

Команды (`python -m auditenv <команда>`):

| команда | что делает |
|---|---|
| `check` | официальная проверка (см. выше) |
| `generate` | заново выгружает `episodes/train` и `episodes/dev` с `index.json` и хешами |
| `validate --root DIR` | независимая проверка выгруженных эпизодов |
| `baselines --split dev` | пять политик в закрытом режиме: P/R/F1/награда/шаги/время |
| `evaluate --split FILE.json --policy pkg.mod:Class` | закрытый прогон любой политики на любом сплите |
| `trajectories` | записывает `trajectories/trajectories.jsonl` |
| `report` | пишет `reports/baseline_report.{md,json}` с разбором сбоев |
| `demo` | пошаговый прогон скриптового аудитора на одном эпизоде |
| `serve` | сервер среды и оценщика (JSON lines через stdin/stdout) |

Прогон независимого валидатора на тысячах сгенерированных эпизодов (28 конфигов: по умолчанию,
D01-D20, 7 стресс-конфигов): `python scripts/validator_sweep.py --per-config 200 --salt любая`.
Результат для соли `sweep-2026-11-21`: 5 600 из 5 600 эпизодов прошли все проверки
(`reports/validator_sweep.json`).

## Эпизод

| файл | видит агент | содержимое |
|---|---|---|
| `public/manifest.json` | да | schema_version, episode_id, base_currency, валюты с экспонентами, period_start/end, timezone, `counts` (ledger_rows, invoices, payments, documents, fx_rates), правила округления, версии |
| `public/ledger.csv` | да | `row_id,timestamp,account,debit_minor,credit_minor,currency,entity_id,invoice_id,payment_id` |
| `public/invoices.jsonl` | да | `doc_id, invoice_id, entity_id, issued_at, due_at, currency, total_minor, line_items` |
| `public/payments.jsonl` | да | `doc_id, payment_id, timestamp, currency, amount_minor, invoice_refs` (`null` у нераспознанных поступлений) |
| `public/fx.csv` | да | `date,source_currency,target_currency,rate`, только будни |
| `public/policy.json` | да | период, правило даты курса, округление, план счетов, правила проводок, типы расхождений, правила сопоставления и награды, лимиты |
| `private/truth.json` | нет | `issues[]`: issue_id, type, affected_ids, expected_amount_minor, currency, tolerance_minor, evidence_sets, interaction_id, variant, description |
| `private/provenance.json` | нет | причинная история генерации и внесённых изменений (см. ниже) |

Деньги это целые числа в минимальных единицах (экспонента из манифеста, например JPY 0, KWD 3),
ROUND_HALF_EVEN только финального результата пересчёта. Время ISO 8601 с явным смещением; пояса
фиксированные. Курсы это десятичные строки. Отсутствующая ссылка это явный `null` (в CSV литерал
`null`). Схемы всех файлов лежат в `schemas/`.

### Формат provenance и независимая проверка чистых книг

* `construction_order`: порядок построения (company, fx, customers, history, distractors,
  error_hosts, clean_books, error_injection, ids, self_check).
* `added_documents` (doc_id), `added_ledger_rows` (row_id) и `removed_ledger_rows` (полные строки).
  Книги до внесения ошибок = публичная книга без `added_ledger_rows` плюс `removed_ledger_rows`;
  документы до внесения = публичные документы без `added_documents`.
* `changes[]`: каждое внесённое изменение (`op`: add_document_and_journal, modify_journal,
  add_journal, remove_journal; `journal.document`; `copy_of` у дубля; `reason` текстом).
* `distractors[]`: каждый отвлекающий случай с видом и документами; `config` и `sampled`:
  конфиг и выбранные из диапазонов значения; `seed`, `attempt`, версии.

`auditenv/validate_data.py` делает такую проверку независимо от генератора: восстанавливает
чистые книги, проверяет их баланс и соответствие политике, своей сверкой находит каждое
расхождение и по каждому набору доказательств заново выводит тип, ID, сумму и валюту.

## Генератор

`generate_episode(seed, config, secret="")` детерминирован: одинаковые сид, конфиг и соль дают
побайтно одинаковые файлы (собственный ГПСЧ SplitMix64, без зависимости от `PYTHONHASHSEED`).
Числовое поле конфига это число или диапазон `[lo, hi]`; значения выбираются из сида и пишутся в
provenance.

Порядок: скрытая история (клиенты, счета, оплаты, частичные оплаты, возвраты, курсы) -> документы
-> чистые проводки по политике -> внесение ошибок как причинных изменений -> самопроверка
(эталонная сверка должна найти ровно истину, чистые книги должны быть без расхождений, иначе
детерминированная перегенерация).

Настройки конфига (полный пример в `configs/splits/judge_matrix.json`):

| ключ | что задаёт |
|---|---|
| `errors.duplicate_invoice`, `errors.payment_allocation`, `errors.fx_conversion`, `errors.period_cutoff` | число ошибок каждого типа, независимо |
| `interactions.fx_partial_boundary`, `interactions.duplicate_misapplied` | число сценариев взаимодействия |
| `variants.payment_allocation` | из `["missing", "partial"]` |
| `variants.fx_conversion` | из `["next_business_day", "previous_business_day", "document_wall_clock_date", "invoice_issue_date", "reverse_pair_rate"]` |
| `variants.period_cutoff` | из `["early", "late"]` (проведён вне периода или не проведён в периоде) |
| `distractors.*` | split_payments, multi_invoice_payments, refund_pairs, recurring_customers, unidentified_receipts, on_account_payments, boundary_documents, cross_currency_payments, legit_partial_payments, boundary_per_cutoff |
| `size.*`, `currencies.*`, `timezone`, `period` | размер, валюты, пояс компании, период |

Взаимодействующие сценарии:

* `fx_partial_boundary`: кросс-валютный платёж у границы суток, применён частично и пересчитан
  по курсу даты «по настенным часам» документа; два расхождения (`payment_allocation` и
  `fx_conversion`) на одном платеже, сумма FX считается от применённой части.
* `duplicate_misapplied`: дубль счёта, на который ошибочно разнесена оплата оригинала
  (`duplicate_invoice` + `payment_allocation`).

Чистые книги (все ошибки 0) всё равно содержат отвлекающие случаи, проведённые правильно:
разбитые платежи, один платёж на несколько счетов, возвраты, подписки с одинаковыми суммами,
нераспознанные поступления, авансы, документы у границы периода, кросс-валютные платежи, законные
частичные оплаты.

Сплиты: `train.json` (сиды 1001-1010) и `dev.json` (2001-2010) выгружены в `episodes/`;
`holdout_sim.json` (900000+, секретная соль) имитирует закрытую проверку: 5 чистых, 5 со
взаимодействиями, 10 смешанных; `judge_matrix.json` (3001-3020) повторяет матрицу D01-D20.

## Контракт среды

| действие | аргументы | результат |
|---|---|---|
| `list_records` | `table`, `cursor` (null или `next_cursor`), `limit` 1..50 | страница записей (счета без позиций) и `next_cursor` |
| `get_record` | `table`, `id` | одна запись |
| `get_document` | `doc_id` | документ (у счёта с позициями) |
| `calculator` | `expression`: десятичные числа, `+ - * / ( )` | десятичная строка |
| `submit` | `findings` | завершает эпизод |

* ID ищутся точно, без смены регистра и псевдонимов. Курсор однозначно задаёт страницу; повтор
  курсора даёт ту же страницу.
* 100 шагов, включая `submit`; `submit` на шаге 100 принимается; 100 исследовательских действий
  без `submit` дают `truncated=true` с пустым ответом. 60 с на эпизод с момента reset, включая
  время политики, затем `truncated=true` с пустым ответом.
* Ошибочное действие тратит шаг и возвращает ограниченную ошибку без путей, сида и закрытых данных.
  После конца эпизода действия ничего не меняют.
* Награда за исследование 0. В `train` терминальная награда и метрики приходят политике; в
  `eval` политика получает 0.0 и пустой `info`, оценка пишется в журнал оценщика.

## Ответ, сопоставление и награда

```json
{"episode_id": "EP-...", "findings": [
  {"type": "fx_conversion", "affected_ids": ["PAY-...", "INV-..."], "claimed_amount_minor": 1234,
   "currency": "EUR", "evidence_ids": ["D...", "FX:2026-10-01:USD:EUR", "GL..."], "explanation": "..."}]}
```

Сначала проверяется структура (`schemas/findings.schema.json`): типы полей, обязательные поля, не
больше 30 выводов, не больше 10 ID доказательств в выводе (до удаления повторов), объяснение до
1000 символов Unicode, `claimed_amount_minor` это целое JSON-число и не bool, `episode_id`
этого эпизода. Нарушение делает весь ответ неверным: награда -1, ошибка в журнале оценщика.

Структурно верный вывод с неверным типом, ID, валютой, суммой или доказательством это FP. Правила
совпадения (код в `auditenv/grader.py`):

* `type` и `currency` сравниваются как точные строки, без смены регистра и обрезки пробелов;
  неизвестный тип просто не сопоставляется;
* `affected_ids` это множество точных ID и должно совпасть с каноническим множеством из таблицы
  типов выше; порядок и повторы внутри списка не важны;
* `evidence_ids` это множество; оно должно содержать хотя бы один полный допустимый набор, а
  каждый ID должен быть существующей публичной записью (row_id, doc_id, invoice_id, payment_id
  или `FX:` ключ); лишние существующие доказательства допустимы;
* сумма: `|claimed - expected| <= τ`, опубликованный допуск τ = 0 для всех четырёх типов (он же
  записан в `truth.tolerance_minor` и в `policy.json -> matching`), так как все суммы это точные
  целые результаты правил проводок и округления;
* сопоставление один к одному: паросочетание максимальной мощности; среди максимальных
  выбирается лексикографически наименьшая последовательность пар `(issue_id, индекс вывода)` при
  сортировке issue_id по кодовым точкам Unicode; TP/FP/FN и награда от порядка выводов не
  зависят; повторный вывод остаётся отдельным FP.

```
TP = пары, FP = выводы - TP, FN = расхождения - TP
P = TP/(TP+FP), R = TP/(TP+FN)  (0 при нулевом знаменателе)
F1 = 2TP/(2TP+FP+FN); 1, если нет ни расхождений, ни выводов; 0, если расхождений нет, а выводы есть
reward = clip(2*F1 - 1 - 0.002*inspection_steps, -1, 1)
inspection_steps = все шаги до submit, включая ошибочные; сам submit не входит
```

Считается точными дробями (`fractions.Fraction`). Пять обязательных свойств награды проверены в
`tests/test_reward.py::RequiredProperties`, атаки в `tests/test_redteam.py`.

## Изоляция и закрытый прогон

```
процесс политики (agent_runner)  <->  харнесс  <->  процесс среды и оценщика (server)
только наблюдения, без соли          пересылает          эпизод, истина, грейдер,
                                      JSON                журнал оценщика в файл
```

* Политика не получает объект среды, эпизод, истину, соль или путь к эпизоду: её процесс
  запускается без `AUDITENV_SECRET`, без ключа и пути журнала оценщика. Падение политики это
  неверный ответ (-1). Адаптер жюри (`make_env`) тоже только клиент процесса среды.
* В процессе политики `auditenv/policy_guard.py` ставит неснимаемый аудит-хук Python: запрещены
  чтение закрытых данных, импорт оценщика и генератора, запись файлов, запуск процессов, сокеты и
  ctypes (`tests/test_hardening.py`). Это дополнительный слой, а не песочница ОС.
* Политика, не ответившая до лимита 60 с, останавливается: эпизод завершается как truncated с
  пустыми findings, следующий эпизод получает новый процесс.
* Записи журнала оценщика подписаны HMAC-ключом конкретного `make_env()`: `last_evaluation()`
  игнорирует чужие и поддельные строки.
* Сервер читает соль из `AUDITENV_SECRET` и убирает её из окружения; ошибки протокола
  возвращаются без трассировок и путей; оценки пишутся только в журнал оценщика.
* Соль входит в ключ генерации: по открытому сиду нельзя получить закрытый эпизод.
* В наблюдениях нет закрытых полей: тесты ищут в них ID расхождений, ID удалённых строк, имена
  закрытых ключей, названия вариантов, причины изменений, сид, соль и пути.

Закрытый прогон своих сидов:

```bash
AUDITENV_SECRET='закрытая-соль' python3.11 -m auditenv evaluate --split hidden.json \
    --policy scripted_auditor --policy my_agent.policy:Agent --out results.json
```

Внешняя политика это класс с методами `reset(seed)` и `act(observation) -> action`.

## Базовые политики и результаты

| политика | что делает |
|---|---|
| `random` | случайные допустимые вызовы с фиксированным сидом, затем 0-3 случайных вывода |
| `reconciliation` | простая сверка: дубли по сумме и клиенту, остаток на 2400-UNAPPLIED-CASH, документы по дате UTC |
| `flag_all` | атака «пометить всё»: выводы по каждому прочитанному документу |
| `oracle` | ответ из истины; только на стороне оценщика |
| `scripted_auditor` | демонстрационная политика: читает всё через инструменты и применяет политику учёта |
| `boundary_guess` | атака для разбора сбоев: помечает документы у границы периода без проверки |

Закрытый прогон на `holdout_sim` (20 эпизодов: 5 чистых, 5 со взаимодействиями, 10 смешанных;
95 эталонных расхождений), `python -m auditenv report` в образе Python 3.11:

| политика | P | R | F1 | micro P | micro R | награда | шаги | время, с (сред. / макс.) |
|---|---|---|---|---|---|---|---|---|
| random | 0.000 | 0.000 | 0.050 | 0.000 | 0.000 | -0.903 | 21.6 | 0.05 / 0.30 |
| reconciliation | 0.112 | 0.313 | 0.163 | 0.127 | 0.411 | -0.688 | 11.4 | 0.05 / 0.24 |
| flag_all | 0.002 | 0.006 | 0.003 | 0.002 | 0.011 | -0.995 | 4.2 | 0.05 / 0.24 |
| oracle | 0.750 | 0.750 | 1.000 | 1.000 | 1.000 | 1.000 | 1.0 | 0.04 / 0.25 |
| scripted_auditor | 0.750 | 0.750 | 1.000 | 1.000 | 1.000 | 0.951 | 25.4 | 0.06 / 0.23 |

P и R усреднены по эпизодам; в 5 чистых эпизодах они по правилу равны 0 (нулевой знаменатель),
поэтому у оракула среднее P = 0.75 при F1 = 1. Micro P/R считаются по суммарным TP/FP/FN. Таблицы
для train, dev, holdout_sim и judge_matrix, разбивка по группам и разбор сбоев лежат в
[`reports/baseline_report.md`](reports/baseline_report.md) и в [`DESIGN.md`](DESIGN.md).

Скриптовый аудитор написан нами по опубликованной политике и показывает, что задача решаема
примерно за 25 шагов из 100. Это не обученная модель, улучшений от обучения мы не заявляем.

## Ограничения

Каждое ограничение связано со сценарием, на котором его можно проверить:

* Скриптовый аудитор решает все наши сплиты (F1 = 1.0 на holdout_sim и judge_matrix), потому что
  знает распределение ошибок генератора. Это проверка решаемости, а не оценка модели; обучение мы
  не проводили и улучшений не заявляем.
* Простая сверка (reconciliation) на чистых книгах всегда находит «что-то»: F1 = 0, награда -1 в
  5 из 5 чистых эпизодов holdout_sim. Так среда и должна наказывать, но это показывает, что
  эвристики без политики учёта здесь не работают.
* Слепое угадывание отсечения периода было выгодным до исправления (см. DESIGN.md, раздел 6):
  `boundary_per_cutoff=0` воспроизводит слабость, тест
  `test_blind_boundary_guessing_was_profitable_without_the_fix` это фиксирует.
* Генератор мог упасть на редком сочетании валют: прогон валидатора нашёл сид, где курс обратной
  пары KWD->JPY давал проводку в 0 JPY (6 из 300 сидов конфига с JPY/KWD). Исправлено и
  перепроверено (DESIGN.md, раздел 6; `test_reverse_pair_rate_never_books_a_zero_amount`), но
  это показывает, что редкие сочетания валют стоит прогонять валидатором на своих конфигах:
  `scripts/validator_sweep.py`.
* Модель учёта упрощена: нет НДС, кредит-нот, списаний, переоценки остатков; часовые пояса без
  летнего времени, праздников нет (только выходные). Сценарии с ними не генерируются.
* Курсы синтетические; тексты позиций и названия собраны из шаблонов, модель может выучить их
  стиль. Закрытая проверка должна менять сиды, диапазоны и соль (`holdout_sim` это имитирует).
* Допустимые наборы доказательств конечны: разумный, но не предусмотренный набор не
  засчитывается (`test_strict_subsets_of_acceptable_sets`, блок 3 тесты 10-11). Правила наборов
  опубликованы в таблице типов и в `policy.json`.
* В части FX-ошибок два варианта внесения указывают на одну и ту же дату курса (например, счёт
  выставлен в предыдущий рабочий день); метка варианта тогда не уникальна, но тип, ID, сумма и
  валюта однозначны (проверяет валидатор, `variants_consistent`).
* Изоляция процессов и аудит-хук не заменяют песочницу ОС: нативный код, уже загруженный
  интерпретатором, хук обойти может. Для недоверенной политики нужен отдельный пользователь или
  контейнер без доступа к каталогу эпизода (так её запускает жюри); проверка ограничений:
  `tests/test_hardening.py`.
* Лимит 60 с измеряется часами процесса среды; на очень медленной машине время политики может
  его исчерпать (C18 проверяет это поведение на коротком лимите).
